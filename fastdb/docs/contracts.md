# Embedded alpha contracts (value format 1, catalog version 2; not a V1 release)

Full V1 scope remains defined in the parent FastDB.md and FastQL.md plans. This implementation is an initial persistent slice; the list below is not a reduction of release scope.

Values at the Rust boundary distinguish null, boolean, int64, finite float64, string, binary, record, object, array, and typed vector bytes. Objects are sorted maps. A stored value is `FDB` followed by byte `01`, then UTF-8 JSON of a fully tagged value tree (`type`/`value` at every node). User objects are nested inside an Object tag, so arbitrary keys cannot masquerade as records. Rust serde_json preserves int64 exactly. This internal format is not yet a cross-language wire contract: JavaScript transport must encode integers losslessly before bindings ship. Vector construction and validation for the five pinned representations are described below.

Collection names and record targets use ASCII case folding, consistent with SQL name lookup. Integer keys and string keys remain distinct. Full documents contain a typed immutable id. UUIDv7 string keys are generated by the engine when id is omitted. Missing fields are absent from the object; explicit null is retained. Nesting is limited to 64. References validate shape and target, not existence.

Every document statement uses an engine SAVEPOINT, including catalog and index changes. Errors roll back the statement; an outer transaction remains usable unless the engine itself aborts it. A failed rollback returns FDB_ROLLBACK with both errors. Multi-statement input is not accepted by execute. BEGIN/COMMIT/ROLLBACK use the same connection for SQL and document operations.

Indexes use real engine tables and B-tree indexes, maintained transactionally. The key column has no affinity: integers and floats compare numerically, booleans index as 0/1, strings remain strings, null/missing do not conflict in unique indexes. Index creation validates all stored values before metadata publication. Rust lookup_index joins indexed IDs to stored documents in one snapshot. AST lowering now chooses a managed index for eligible leading-collection equality or constant IN-list predicates. Other predicates still scan through Turso; broader planning remains pending.

The initial Rust error categories have stable identifiers exposed by code(). Engine errors retain their native message. Busy and stale-snapshot contention use FDB_BUSY and FDB_BUSY_SNAPSHOT, and interruption uses FDB_CANCELLED; native constraint/foreign-key/trigger-raise variants use FDB_CONSTRAINT; other engine failures still use FDB_ENGINE, with finer subcategories pending. SELECT/RETURNING produce rowsets with all/first/exactly_one helpers; a collection document occupies one Object-valued column named document. Commands without RETURNING have no rows. Ordinary SQL columns retain engine names, types, and positional ordering. Final duplicate-column and client/wire contracts remain release gates.

Collection SELECT now lowers through the pinned AST for the subset described in status.md. Direct field projections preserve typed values; scalar expression operands map booleans to integers. Missing nested reads return NULL. Duplicate projection names fail with a request to use AS. Record ORDER BY compares target names, then integer keys numerically before string keys. Mixed record/scalar ordering and derived typed expressions are not frozen. Implemented SQL-shaped collection writes use the same savepoint/validation/index path as document operations. Unsupported read/write forms still reach a conservative managed-name guard, which rejects some harmless strings. Complete AST-aware lowering and dependency authorization before claiming ordinary SQL preservation or enabling all write paths. Do not expose raw engine connection handles through FastDB.

SQL-shaped VALUES/SET writes preserve a direct typed parameter or copied document field without coercion. Other scalar expressions retain engine types, including integer 0/1 for SQL FALSE/TRUE; use a typed Boolean parameter for a boolean validator. Multirow assignments are evaluated from pre-update documents before any changes. Nested SET creates absent object parents and rejects non-object parents. UNSET removes the path and final-candidate validation still applies. Quoted keys containing dots stay distinct from nested paths; overlapping targets are rejected before writing. SQL-shaped and object INSERT/UPDATE/DELETE, including UPSERT, support typed RETURNING projections.

Record literals in expression positions and type::record(target,key) compile to a private pure constructor. Direct record projections retain the typed value; arbitrary type propagation through scalar functions remains incomplete. The Rust parameter map addresses anonymous/numbered slots as ?1, ?2, etc. The pinned engine rejects namespace-like $name::suffix parameters; FastDB preserves that baseline error.

Catalog writes now use version 2. Missing version markers from the initial prototype are read as version 1; version 1 remains readable when it has no CHECK metadata. Unknown versions and version-1 entries containing CHECKs are rejected. Publishing validation metadata upgrades its catalog entry atomically. This is backward reading of the initial representation, not a general migration runner or a completed upgrade rehearsal.

UPSERT requires a typed id and either inserts or shallow-patches that id atomically. Target-form bodies omit id. DROP INDEX removes both its managed storage and catalog entry; DROP TABLE on a collection removes all owned indexes and validation metadata. Both are transactional, and collection drop leaves weak references unchanged. REMOVE FIELD retains stored values and indexes. A validator cannot change an indexed path into an incompatible object/array or non-object parent. INFO returns logical metadata under an info-valued column; its serialization remains provisional.

Field CHECK evaluates a side-effect-free SQL expression against bound final-candidate fields. False and SQL NULL fail; missing optional and permitted-null fields skip their attached check. New/overwritten definitions validate existing data before publication. User parameters, database reads, aggregates, windows, current-time expressions and non-eligible functions are rejected even on an empty collection. The approved function/operator set is listed in status.md; ordinary relational SQL CHECK constraints retain engine behavior. New CHECK metadata requires catalog version 2 to avoid silently weakening validation in version-aware older builds.

## Object-write expression subset

Object bodies evaluate nested scalar calls/operators and typed record, array and document-path helpers described in status.md. UPDATE bodies read the pre-update document; predicate patches evaluate all candidates before mutation and roll back the statement on validation/index failure. UPSERT evaluates its explicit ID once, then evaluates patch fields against the existing document or an empty document on insertion. Missing field reads are null; coalesce/ifnull evaluate lazily and retain the chosen value's type. Scalar calculated comparisons use engine integer 0/1, while literal booleans and doc::has retain Boolean values. Composite operands are rejected by generic scalar functions/operators; record comparison uses logical identity. Expression depth is limited to 64. SQL SELECT/SET/VALUES now support the helper subset below; broader expression propagation remains incomplete.

## Typed SQL helpers

Record extractors, array::new/append and doc::get/has accept typed fields, bound values and nested helper results in collection SELECT/SET/VALUES. doc::row(alias) yields the collection document or null for an unmatched outer join. Parentheses and lazy coalesce/ifnull preserve logical values; missing and explicit-null paths both read null, while doc::has distinguishes presence. Helper result projections retain types, including Boolean from doc::has. Ordinary SQL TRUE/FALSE still evaluate to integers. These functions do not guess whether a String or Binary contains encoded document data. The implementation currently embeds encoded typed parameter occurrences into the lowered AST; this is not a frozen prepared-statement or resource-limit contract. CASE now preserves selected typed branch values; full comparison propagation remains pending.

Searched and simple CASE are accepted in object-write expressions and SQL SELECT/SET/VALUES. The base of simple CASE is evaluated once; branches are tested in order, and unselected result expressions are not evaluated. No matching branch without ELSE returns null. SQL conditions retain the pinned engine scalar rules. Object conditions use the same SQL truth conversion and the existing typed record identity comparison. Existing nesting limits apply to object CASE trees.

## INSERT SELECT

An explicit target column list maps SELECT results positionally into new documents. The supported source subset is recorded in status.md; collection fields and typed helper results retain their logical values. Source rows are collected before any insertion, including when source and destination are the same collection. A column-count mismatch is an error even for an empty source. Each candidate passes the ordinary insert validation/index path, and all candidates share a statement savepoint. RETURNING * returns inserted documents. Broader source queries and bounded-memory execution remain release work.

Ordinary relational INSERT targets can also consume the supported collection SELECT subset. The lowered source runs inside a single native INSERT statement, retaining target affinity, constraints, triggers, conflict policies, UPSERT and native RETURNING. Binary values become their raw bytes, booleans become integers, and records retain their canonical encoded BLOB identity. Use `record::id(id)` explicitly to copy a record key into an ordinary integer or text column. Object, array and vector values have no implicit native scalar conversion. Native ABORT and FAIL dispositions remain distinct: FAIL can retain earlier inserted rows. Fetched projections and broader collection source forms remain unsupported.

## RETURNING projections

SQL-shaped INSERT/UPDATE evaluate RETURNING against final documents, and DELETE against deleted snapshots. Named expressions retain the SELECT lowering types; stars return Object-valued document columns. Empty rowsets include column metadata. Aggregates, windows and subqueries are rejected. Projection failures roll back the statement without delivering partial results. A runtime extension/helper error may also abort the outer transaction in pinned Turso, consistent with the engine-abort exception above; the connection can start a new transaction afterward. Observed transaction-state reporting is available below; detailed error disposition remains unfinished.

Object/DOCUMENT INSERT, target and predicate object UPDATE, UPSERT, and direct DELETE share the RETURNING snapshot contract. Invalid projection syntax is a statement error and rolls back its write. RETURNING accepts result expressions only; it cannot add a data source or a nested query. A missing target still returns projection metadata with zero rows.

## Transaction observations

Connection::transaction_state() returns Active when the engine autocommit flag is off, otherwise Autocommit. execute_report() returns the original typed result/error plus before/after states, including failures. Active includes outer savepoints and does not promise a subsequent commit succeeds; Autocommit does not distinguish commit from rollback. Operations on one connection must be serialized by the caller. The CLI includes transaction.before/after on every executed statement's JSON line. These observations let a caller detect that an outer transaction ended after an error without parsing error messages. They do not infer the cause of the transition or replace release-level transaction failure testing.

## Scripts

Connection::execute_batch(script) returns BatchExecution entries containing UTF-8 byte offsets and ExecutionReport values. It stops at the first execution error, retains all earlier reports, and leaves transaction control to the script/caller. Lexical splitting is completed before execution, so an unterminated quote/comment or unbalanced delimiter produces an error before mutation. Earlier successful statements are not automatically undone by later execution errors. Scripts currently have no bound-parameter argument; individual execute calls retain parameter support.

The CLI defaults to multiline semicolon-delimited scripts and stops on error. --line selects legacy line-oriented continuation. Both modes exit nonzero if any statement fails; script JSON lines also include offset. A trailing statement may omit its semicolon. These in-memory script/report APIs still require bounded execution and a frozen wire contract before release.

## One-hop forward links

record::fetch(reference) is accepted as a top-level SELECT projection and returns one target Object or Null. Connection::fetch_records resolves a slice of typed records/nulls in the same order and preserves duplicates. Missing records/tables produce Null; incompatible non-null inputs fail. Reads share one transaction snapshot, including the outer query when called through SELECT. Returned record fields are not recursively resolved.

Collection keys retain typed identity. Relational targets need one explicit TEXT or INTEGER primary key, matched by reference key type; their returned primary keys retain native SQL types. Resolution groups/deduplicates targets and reads at most 128 keys per target batch. More than 16,384 reference positions fails with FDB_LIMIT. Each resolver invocation also limits fetched target values and expanded output values separately to 64 MiB, measured as the sum of tagged Value JSON bytes (without array delimiters or the storage prefix). Output accounting includes duplicates and nulls, and completes before cloning output documents. Target accounting runs before retaining each decoded document. Neither budget includes reference keys, container overhead, the current engine row or the already-materialized outer query. All fetch projections in one lowered SELECT are flattened into one resolver call and share its reference-count and byte budgets. These are not total query-memory or time budgets. Fetch is unavailable in nested expressions, filters/orderings on fetched values, write expressions and RETURNING. Complete comparison/collation, schema-race, planner/resource and release coverage remains pending.

## Dense vectors

Value::vector32(&[f32]) and Value::vector64(&[f64]) construct typed dense values in the pinned engine encoding. vector_dimensions() checks and returns dimensions. Values must contain 1..65,536 finite components in a supported representation; field vector<N> additionally requires exactly N components. Binary remains distinct from Vector on writes, even when its bytes are valid vector data. Explicit vector constructors may consume engine text or validated dense blobs. Validation applies to evaluated candidates and existing values when defining fields.

Collection/object vector32/vector64 constructors preserve typed values. Exact-distance and extraction functions delegate to the pinned engine, preserving its floating-point results/errors. Plain SQL retains native types. Scalar indexing and generic scalar treatment of vectors are rejected. Sparse32, quantized8 and bit encodings are also supported as described below; wider numerical/resource/platform contracts remain pending.

Typed vectors also support the pinned sparse32, float8 and bit encodings. Sparse indexes must be strictly increasing and below dimension; quantization metadata/components must be finite; lengths, trailing metadata and padding must be valid. Constructors preserve native bytes. Slice/concat preserve typed results, with native unsupported-format errors for bit/float8 operations. FastDB corrects the pinned sparse-concat index-offset defect in its typed frontend; ordinary SQL remains delegated unchanged. These formats retain the same positive-dimension and 65,536-dimension limit and need wider fuzz/numerical/platform qualification before release.


## Initial bundled string functions

The prototype embeds fixed JavaScript source through pinned `rquickjs = 0.12.2` (MSRV 1.87), with its bundled native C runtime. The public catalog currently contains:

| Function | Contract |
| --- | --- |
| `string::slugify(text)` | Apply NFKD normalization, remove Unicode combining marks, lowercase, replace runs outside ASCII `a-z0-9` with `-`, then trim leading/trailing hyphens. This is not general transliteration; non-Latin input may produce an empty string. |
| `string::normalize(text, form)` | Unicode normalization with explicit, case-sensitive `NFC`, `NFD`, `NFKC` or `NFKD`. |

Both require string arguments, reject null/non-string values, and return a typed string. They work through the shared SQL helper and object-write expression paths; they are not currently CHECK-eligible. Successful results are deterministic for fixed inputs and the pinned bundle/runtime Unicode tables. Resource-budget failures can depend on machine load.

Each call creates a fresh runtime with an 8 MiB JavaScript heap limit, 256 KiB stack limit, 65,536-byte UTF-8 input/output limits, and an interrupt handler that stops after 1,000 allowed polls or a 100 ms elapsed deadline. Interrupt polling is cooperative, not a hard real-time deadline. Output size is checked after conversion to a Rust string; these limits do not bound total query memory or total execution time across many rows. Settings use the [rquickjs Runtime API](https://docs.rs/rquickjs/0.12.2/rquickjs/struct.Runtime.html); allocator features that bypass its heap limit are not enabled.

Only the compiled-in source is evaluated. Inputs pass as function arguments, never interpolated code. No public user-JavaScript API, module loader, host I/O or database callbacks are installed. The runtime includes JavaScript language built-ins; this is a fixed-function execution boundary, not a general-purpose user-code sandbox.

Direct object-expression argument errors use validation errors; input/output, execution and recognized allocation/stack failures use `FDB_LIMIT`. Runtime initialization or unexpected bundle failures use storage errors. SQL UDF failures pass through the engine error path and can abort an outer transaction, as documented above; error classification is not yet a frozen cross-language contract.

Fresh runtimes trade performance for isolated calls. Benchmarks, full dependency/license/security review, Unicode upgrade compatibility, cancellation integration, native C packaging and non-Linux platform tests remain release gates. The two-function catalog does not complete V1 runtime qualification.


## Initial collection grouping

Collection SELECT and INSERT SELECT support GROUP BY scalar expressions, positive projection ordinals, and HAVING expressions through the pinned engine. Keys and aggregate arguments use SQL scalar lowering; missing fields and explicit null share a SQL NULL group, and numeric/boolean scalar coercions follow that lowering. Result field projections retain their tagged type. SQL aggregate outputs retain native scalar types, and aggregate DISTINCT/FILTER clauses use the existing expression lowering.

HAVING resolves projected aliases, including aggregate expressions and typed helper inputs, with alias precedence matching the pinned relational frontend. Qualified source fields retain their source meaning. GROUP BY named aliases are supported as described below; qualified paths retain stored-field meaning. Composite grouping keys still fail scalar conversion; full typed equality, GROUP BY alias precedence and broader query semantics remain V1 work. Scalar DISTINCT is described below; CTEs and UNION ALL are described below; set operators are described below; broader compound qualification remains unfinished.


## Mixed query star projections

In collection-aware SELECT queries, relational `alias.*` expands to the pinned engine's visible columns in their native order. Expansion prepares a standalone source SELECT for metadata without executing it, then generates qualified column expressions. This also supports ordinary views. Collection stars produce one typed `document` column per collection source; unqualified `*` expands sources in FROM/join order. Outer-join null extension and relational scalar/blob types remain native.

Expanded columns participate in GROUP BY ordinals and INSERT SELECT width/validation checks. Existing duplicate-result-name rules still apply: ordinary result queries require unique names, so overlapping stars or multiple collection document stars may require explicit projections with aliases. Positional INSERT SELECT can accept duplicate source names. NATURAL/USING joins and derived/table-function sources remain separate unresolved query features. Full concurrent schema-change and view-dependency authorization qualification is still pending.


## Initial collection windows

Collection SELECT and INSERT SELECT lower scalar window arguments, PARTITION BY and ORDER BY expressions, inline OVER clauses and named WINDOW definitions through the pinned engine. Row-number, sum and count windows have differential integration coverage. Collection field output projections retain their tagged values; window arguments and results currently use native SQL scalar types. Composite arguments and full typed window semantics remain unqualified.

Pinned Turso rejects custom frame specifications and `lag` as tested; these engine errors are preserved. Frame expressions are lowered but no support beyond the native baseline is promised. Aggregate-local ORDER BY combined with OVER is rejected by the frontend before reaching an upstream assertion. Windows remain invalid in RETURNING and WHERE, and are not CHECK-eligible. Broader window functions, named-window inheritance, collation, resources and release-level coverage remain pending.


## Cooperative engine interruption

`Connection::interrupt_handle()` returns a cloneable, thread-safe weak `InterruptHandle`. Calling `interrupt()` requests interruption of currently active root engine statements. False means the connection has been dropped; true means the connection was live, not that cancellation was observed. Idle requests do not cancel subsequent work. Handles do not retain the connection or expose other engine operations.

Direct engine interrupts now surface as `FDB_CANCELLED`. The frontend collects rows using the pinned engine's callback runner because its convenience `run_collect_rows` method conflates Interrupt and Busy. Actual Busy and BusySnapshot errors now use FDB_BUSY and FDB_BUSY_SNAPSHOT. Existing migration/error wrappers still apply, and clients must inspect transaction observations after a failure. Tests cover interrupted relational writes leaving no partial rows and successful reuse; no general promise to retain an outer transaction is made.

Interruption is cooperative and connection-wide. It is not tied to a request ID, and racing request boundaries may affect whichever engine statement is active. It does not dequeue work, interrupt parsing or Rust validation, or directly stop bundled JavaScript while inside its runtime. Multi-stage FastDB operations may have gaps without an active engine statement. Per-operation cancellation tokens, AbortSignal integration, deadline/resource budgets, broader interrupted document/index writes and commit/checkpoint qualification remain release work.


## Persisted binary64 decoding precision

The frontend enables serde_json's `float_roundtrip` feature when decoding tagged persisted values. Without it, the former reader changed some finite values by one binary64 unit: `2.291712365432881e-9` decoded to bits 4477615450478306381 instead of the original 4477615450478306380. The writer already emitted a round-trippable decimal; this is a reader correction, with no stored-format or catalog-version change. Existing original payloads decode with the corrected precision. Values already read and rewritten with the old rounding error cannot be reconstructed from the rewritten payload alone.

Tests compare binary64 bits, including signed zero, finite extremes and subnormals, across encode/decode and database close/reopen with scalar index lookup. Transfer-v1 continues using hexadecimal binary64 bits. Cargo feature unification enables the precision option for serde_json in the combined FastDB build; dependency versions and upstream source remain unchanged. Wider numerical/index/collation and upgrade qualification remains part of V1 release work.


## Standalone typed parameters

A source-free SELECT without CTEs or compound branches now enters typed lowering when parameters include a Boolean, Record, Object, Array or Vector. Direct parameter projections preserve those tags, including numbered placeholders. Ordinary scalar-only SQL continues through the native path. Standalone alias predicates use the original scalar expression rather than treating encoded typed projection bytes as SQL truth values; typed helper arguments can retain alias values. Fetched aliases remain ineligible for predicates/grouping because fetching occurs after the engine projection.

DISTINCT is accepted for a source-free SELECT because its input has at most one row; this does not enable DISTINCT over collection projections or define composite equality. Missing SQL names still fail. Full source-query alias/type propagation, composite ordering/grouping and broader CTE/compound queries remain V1 work.


## Reference target validation

Every evaluated Record value now validates its target with the same logical-name rules as indexed references: nonempty, no NUL, and no case-insensitive `__fastdb_` or `sqlite_` prefix. This applies recursively inside arrays/objects, regardless of field declarations or indexes. String keys must remain nonempty; target existence is not required for weak forward references. Target casing remains accepted, and scalar index keys, record::table and fetch resolution use the canonical target identity.

The former prototype validator checked only empty target/key strings, allowing invalid nested references on unindexed writes. Those writes now fail before mutation through insert, patch, upsert, SQL-shaped writes and imports. Previously stored invalid references are also rejected when decoded; they require correction with a retained earlier prototype before upgrading. No stored-format or catalog-version change is introduced. This tightens an invalid-value gap and does not promise automatic repair or migration-free upgrades.


## Partial-write interruption evidence

Deterministic progress-callback tests now interrupt collection UPDATE, DELETE and INSERT SELECT after the engine's total-change counter advances. In these pinned-engine cases, statement rollback restores documents and managed index entries. If an explicit outer transaction existed, it remains active and retains prior uncommitted work; later writes and explicit rollback still work. This is evidence for those interruption points, not a universal outer-transaction guarantee for every error. A partially executed index build removes its catalog declaration and physical storage on interruption and can be retried successfully. These tests use engine progress callbacks only in test code and do not add a public callback or cancellation API.


## Batch result visitation

Rust `visit_batch(script, visitor)` visits each owned BatchExecution between statements. Returning false stops successfully; a visitor error returns that error. Both leave earlier execution/transaction effects intact. Statement execution errors are visited once and stop the script regardless of the visitor's return value. Full lexical splitting precedes any execution. `execute_batch` now collects through this shared path.

The native Node bridge uses visitation to encode each result before advancing, preserving earlier reports and stopping if a value cannot be represented by the portable encoding. This does not add implicit rollback for result-consumer errors. Sync/async Node executeBatch return per-statement errors as data; pre-execution lexical errors use the normal thrown/rejected error envelope.


## CLI output failure ordering

Script execution emits and flushes each statement's JSON report before advancing. A write, flush, or serialization failure stops execution and exits nonzero through the CLI error path. Previously executed effects remain intact: output delivery is not a commit acknowledgement and does not undo committed statements. If an explicit transaction is still active, normal connection close rolls it back; a COMMIT already executed cannot be undone by failing to deliver its report. The line-oriented mode also propagates output errors instead of panicking and stops reading further statements on those errors.

The CLI no longer retains reports for the entire script. Input and lexical splitting still materialize the full script, and each statement's rows and JSON report remain materialized. This is per-statement delivery, not bounded-memory row streaming or an interactive shell.


## Qualified nested SELECT paths

The collection SELECT lowerer accepts qualified paths beyond the pinned parser's three-name limit, such as `u.profile.address.city`, with up to 64 field segments after the source name/alias. Each quoted segment remains one literal key, including dots or doubled quote characters. Whitespace/comments between segments do not affect resolution. Typed projection results, scalar predicates, joins, ordering and managed equality-index candidates use the same resolved path. Missing fields return NULL. Unknown source qualifiers fail; nested paths do not imply record traversal. Ordinary one-, two- and three-part SQL names retain their existing parsing.

The same path expansion applies to SQL-shaped write expressions/predicates, INSERT SELECT sources, and object/SQL RETURNING projections. UPDATE assignment targets retain their existing field-path normalization. Validation and index maintenance still run through normal atomic writes, and RETURNING reads the final or deleted snapshot. Derived sources/CTEs and array subscripting remain separate unfinished work; the path limit is not a total query-memory budget.


## Expression column labels

Collection expression labels restore public namespace function names and dotted qualified paths from the internal AST representation. Conversion applies to function tokens, not substrings inside string literals or quoted field names. A deep expression such as `upper(u.profile.address.city)` therefore exposes a normalized dotted expression label rather than an internal path function. SELECT and RETURNING use the same naming path. Explicit AS aliases remain the recommended stable application-facing labels; normalized whitespace and identifier quoting are not a promise to reproduce the submitted SQL text byte-for-byte.


## COUNT and composite values

In collection queries, non-DISTINCT `COUNT(expression)` counts any supported non-null value, including arrays, objects, records, binary values and vectors. Missing fields behave as null and are excluded; false, empty arrays/objects and empty binary values are present and count. `COUNT(*)` still counts rows. Typed parameters and helper results follow the same null-presence rule.

This also applies to the supported window and grouped INSERT SELECT paths. FILTER excludes a row before evaluating its aggregate argument; an invalid helper input on an included row still raises an error. A failed grouped write follows the normal validation and transaction rules.

`COUNT(DISTINCT expression)` additionally requires the scalar equality rules below. Plain COUNT support does not define generic composite equality or enable composite DISTINCT. Use a scalar projection when distinctness is required.


## Scalar DISTINCT

Collection DISTINCT now groups scalar comparison values while retaining an original typed projection as each group's representative. Numeric integer/float equality and boolean 0/1 comparison follow the pinned engine; null and missing projections deduplicate together. Text stays distinct from numbers, record target names compare case-insensitively with typed keys, and binary values retain their own representation. Equivalent rows with different numeric/boolean representations may return any representative; callers needing a fixed type should project an explicit conversion. Explicit scalar COLLATE expressions retain native collation behavior.

An outer grouping query performs deduplication after source aggregates/windows, followed by ORDER BY and LIMIT/OFFSET. INSERT SELECT can consume these results through normal validation and atomic writes. Objects, arrays, vectors and fetched documents still have no generic DISTINCT equality in V1; use scalar projections. This implementation can require engine temporary grouping/sorting storage and still needs resource/performance qualification. It does not enable CTEs/derived user sources or freeze broader typed comparison semantics.


## Collated ordering aliases

ORDER BY resolves projected names and positions through COLLATE and single-expression parentheses, preserving those wrappers when lowering typed values or DISTINCT outputs. A projected alias takes precedence over a same-named stored field in these forms, matching the pinned relational frontend. Qualification still addresses a source field. ORDER BY alias references inside supported arithmetic and scalar/helper expressions now resolve to the projected value too. DISTINCT evaluates output-dependent ordering outside grouping and carries independent source inputs through its inner query, avoiding a second evaluation of volatile projections. Aggregate/window operations over output aliases fail explicitly; WHERE/GROUP BY/JOIN ON alias substitution is described below; derived-source type propagation remains incomplete.


## Ordinary SQL literals in the fallback guard

The fallback managed-name guard uses a parsed, guard-only copy for covered SELECT and ordinary write contexts. It removes string value literals from that copy before scanning names, including nested/derived queries and CTEs. It never executes the copy: native preparation, parameters, result names and execution still use the original SQL. Consequently ordinary values such as 'users', '__fastdb_catalog' or 'writable_schema' are not mistaken for table/PRAGMA references. Identifier roles remain guarded, including SQLite's single-quoted table names.

Unknown/unparsed statement forms retain the original conservative scan. Value expressions in CREATE/ALTER column defaults, CHECK/generated definitions, index keys/predicates and UPSERT clauses are also covered. Their object/column/constraint/reference names remain guarded. Trigger WHEN expressions and supported SELECT/INSERT/UPDATE/DELETE body expressions are covered as well, while trigger names, targets and body object references remain guarded. PRAGMA arguments, table-function arguments and other uncovered contexts remain conservative. This reduces literal false positives; it does not replace the remaining name/reference guard with a complete authorization or dependency boundary.


## Initial interactive CLI

Terminal stdin opens an interactive prompt automatically; piped input retains script mode. --interactive and --script force either mode; --line remains the legacy per-line mode. Explicit input modes cannot be combined with one another or with import/export/migration operations. Plain prompts go to stderr; the Unix editor renders on the controlling terminal. JSON reports remain on stdout. The primary prompt shows an active transaction; continuation prompts indicate buffered input.

The shared parser waits for semicolon-terminated statements, including multiline strings/documents and complete trigger bodies. Each completed input buffer runs as a batch, stopping at its first execution error; later input remains available for recovery or ROLLBACK. Any statement error causes a nonzero eventual exit. Byte offsets are relative to the submitted buffer. EOF submits a final unterminated statement through normal script execution and reports lexical errors if incomplete.

A line containing .clear discards pending input without changing transaction state; .quit/.exit discards pending input and exits; .help prints help. These exact command lines are recognized even inside an unfinished buffer. Normal connection close rolls back an active transaction. Output/prompt I/O errors stop the session. Unix terminal editing and history are described below; broader signal/platform/resource qualification remains unfinished.


## CLI SQL input limits

SQL input defaults to a 16 MiB UTF-8 byte limit; --max-input-bytes N selects a positive limit. Script mode bounds the entire input before execution, line mode bounds each line, and interactive mode bounds each line and the accumulated pending buffer. Newlines/comments count toward the limit. Import/export and migration operations retain their existing independent limits and reject this SQL-input option.

Plain input reads retain at most one extra byte to detect overflow, checking length before UTF-8 decoding. The terminal editor first materializes its editable line; its live buffer is outside this submission limit. Overflow emits FDB_LIMIT with the observed transaction state and exits nonzero. No oversized script/buffer prefix or remaining tail is submitted as SQL. Earlier committed line/interactive statements remain committed; normal connection close rolls back an active transaction.

This bounds input byte lengths, not total allocation or execution/result memory: interactive input can retain a pending buffer and a separate bounded line, parser/JSON copies add overhead, and query results remain materialized. Rust/Node execution limits, deadlines and full resource qualification remain separate work.


## Multi-connection contention

FDB_BUSY identifies native writer/lock contention. FDB_BUSY_SNAPSHOT identifies a read snapshot that cannot be promoted to a writer after another connection commits. The latter requires ending the stale transaction before attempting work in a fresh transaction; retrying only the statement in that snapshot is insufficient. No automatic retries are performed. Callers must inspect transaction observations and choose safe retry/rollback behavior for their operation. Both codes retain the native error message and replace the former generic FDB_ENGINE classification for these variants.

Deterministic two-connection tests verify uncommitted document/index invisibility, retained reader snapshots across a writer commit, rejected stale writes without partial index changes, and index-build contention followed by rollback/commit and successful retry/reopen. This is controlled transaction-overlap evidence, not broad concurrent stress, cross-process/crash qualification or a universal transaction-state guarantee.


## Native constraint error category

FDB_CONSTRAINT groups the pinned engine's Constraint, ForeignKeyConstraint and Raise error variants, retaining their native messages. It replaces the former FDB_ENGINE classification for those variants and reaches the CLI/Node envelopes through the same Error::code mapping. ## GROUP BY ordinal resolution

Collection GROUP BY resolves a positive integer position against the original projection, before typed values are encoded. Parentheses, a single unary plus directly on a numeric literal, and surrounding COLLATE follow the pinned engine's ordinal rules. Scalar grouping therefore combines numerically equivalent integer/float/boolean values and honors explicit text collation. The selected result retains its typed representation; the representative of equivalent values is not specified.

Zero, negative integer literals and positions beyond the projection list fail. Floating literals and compound constant expressions remain expressions; the pinned engine does not recognize +(2) or -(-2) as ordinals. A projected integer constant is protected from being interpreted as a second ordinal in generated SQL. Ordinal substitution selects the original expression without resolving its source names against unrelated projection aliases. Named GROUP BY aliases are covered below; document-star grouping, broader composite grouping and full expression/type qualification remain pending.


ORDER BY uses the same pinned-engine ordinal recognition as GROUP BY: parentheses and COLLATE can wrap a position, and a single plus directly on an integer literal is allowed. Expressions such as +(1), +(+1), -(-1), 1.0 and 1+0 remain constant expressions rather than column positions. This matters when later ordering terms determine the row order. Integer parsing follows the pinned engine's platform-sized unsigned range; recognized zero, negative and out-of-range positions produce FDB_VALIDATION in collection lowering, with or without DISTINCT. Ordinary relational delegation retains its native error classification. General expression/alias resolution remains separate from numeric ordinal recognition.

CTE names shadow unqualified collection names; main-qualified collection sources bypass that shadowing. Nested WITH clauses receive their own scope. Native CTE expressions retain native evaluation and their output metadata is inspected without executing them. Bound Binary inputs in native CTEs are embedded as raw byte literals, with output names retained, so a shared parameter can still use encoded comparison keys in a collection index predicate. Source-form INSERT INTO target ... WITH ... SELECT uses the existing collection validation or native-target execution path, including RETURNING and rollback.

Current collection CTE support requires references to earlier definitions; forward references, recursive collection CTEs, fetched inner projections, scalar/correlated queries remain unsupported or unqualified; compound operators are described below. The pinned native engine also rejects recursive CTEs. Leading WITH ... INSERT SELECT is described below; leading-WITH UPDATE/DELETE remain unsupported for collections, while the typed VALUES extension is described below. Broader scope, volatile-expression, planner and resource qualification remains open.

## Leading WITH INSERT SELECT

A leading nonrecursive WITH on INSERT SELECT now uses the same typed source lowering as source-form WITH. Collection targets retain positional field mapping, evaluated-value validation, index maintenance and statement rollback. Native targets retain their conflict policies, native RETURNING and one-statement execution. Native-only statements still delegate their original SQL.

The managed-source route scopes the leading CTE definitions to the SELECT source. Subqueries and table-membership expressions in native UPSERT/RETURNING clauses are rejected before execution on this route, preventing a CTE reference from silently resolving to an unrelated physical table after lowering. Ordinary target-column RETURNING remains supported. Leading-WITH UPDATE/DELETE, dual outer/source WITH scopes and broader cross-clause CTE typing remain unfinished; VALUES support is described below.

## CTE cancellation verification

Controlled cancellation checks now cover early mixed-CTE read/write execution and collection inserts from CTE/derived sources after engine change counters advance. At the tested points, interruption propagates as FDB_CANCELLED, existing outer transactions remain active, prior work survives, and no partial target documents or index entries remain. Retrying after clearing the test hook succeeds; explicit rollback restores the committed state. These tests do not guarantee outer-transaction preservation for all engine errors or establish a complete request deadline.

## Mixed native-column range comparisons

For `<`, `<=`, `>` and `>=` between a preserved logical value and an ordinary SQL column, lowering converts the logical operand to a raw SQL scalar while retaining the native column's affinity and collation. Binary values compare by their payload bytes. Record/scalar ordering is rejected unless an operand is NULL, in which case the comparison is unknown. Native column parentheses, unary plus and explicit COLLATE retain their SQL roles. This path does not establish arbitrary native expressions or all wrappers around logical operands. The native-column BETWEEN extension is described below.

## Native-column BETWEEN document bounds

A native column may now use preserved document values as either or both BETWEEN/NOT BETWEEN bounds. The native BETWEEN operation retains the column's affinity and collation; typed bounds convert once to raw scalar payloads and reject non-null record/scalar ordering. NULL retains three-valued comparison behavior. Parentheses, unary plus and COLLATE around the native column retain their SQL roles. The logical-left/native-column-bounds extension is described below; arbitrary expressions in every position remain unqualified. Conversion also reads the native column to enforce NULL-aware record rejection; volatile expressions behind native views/derived columns are not yet qualified for evaluation counts.

## Terminal editing and history

With Unix terminal stdin/stderr and an available controlling terminal, the CLI uses pinned Rustyline 15 for editing and multiline history recall. Piped input and redirected-stderr sessions retain plain input. Ctrl-C during a prompt discards the current line and pending multiline buffer without changing transaction state. Ctrl-D follows the existing EOF rule, including attempting any pending trailing SQL. Running-query cancellation is described below.

History defaults to memory only. `--history PATH` requires terminal mode and loads/saves that file; missing files are created on a normal session return, including a return after SQL errors. History stores submitted buffers, including failed statements, but excludes cleared input, dot commands, entries starting with whitespace and new entries over 64 KiB. It retains at most 100 entries and rejects loading nonregular files or files over 8 MiB. New files have owner-only permissions on the tested Unix platform; existing permissions are retained. Save/load failures are reported as CLI errors. Database/main-WAL-SHM path collisions, including existing Unix aliases, are rejected before opening the database and rechecked before saving. History files are not a transactional log, and concurrent-session history merging is not qualified.

A real pseudo-terminal regression verifies editing keys, multiline recall, persistence across sessions, private file creation, prompt Ctrl-C with an active transaction, EOF, submission-limit rejection and JSON stdout isolation. It requires Python 3 with Unix pty support. Linux is verified; other terminals/platforms and complete editor-memory bounds remain release work.

## Interactive CLI query cancellation

Edited Unix terminal sessions install a SIGINT listener backed by pinned signal-hook 0.3.18. The async-signal handler wakes a regular thread, which uses FastDB's weak interrupt handle; it performs no database operations in signal context. Ctrl-C during active engine execution requests interruption. An interrupted statement emits FDB_CANCELLED with observed transaction state, stops the rest of that submitted batch, and leaves the interactive session available for another command. The session still exits nonzero after any failed statement. Prior committed work is not undone, and engine errors may abort an outer transaction; inspect the result state.

Prompt Ctrl-C still clears pending input. The listener shuts down and joins on session exit. Idle interrupt requests do not poison subsequent engine statements, but delivery is asynchronous and not bound to a request ID. This is not a deadline across frontend parsing, lowering, output delivery or cleanup. Nonterminal input modes and other signals retain their existing process behavior. Real-terminal tests cover cancellation of a large aggregate read inside an outer transaction, prior-work retention at that tested point, native INSERT rollback, skipped batch tails and successful subsequent queries. Broader signal timing, platform and cancellation-resource qualification remain open.

## SELECT profiling

`Connection::profile_select(sql, params)` executes one SQL SELECT and returns `ProfiledQuery { result, metrics }`. Results retain the ordinary typed values and bindings. Metrics come from the primary engine statement after completion: physical rows read/written, fullscan/index steps, executed VM instructions, sort operations and B-tree seeks. They exclude catalog/lowering helper statements, Rust decoding, transport and any other connection work. Counters reset for each call and are the pinned engine's unsigned 64-bit counters, not logical document counts or query-time measurements.

Non-SELECT statements, multiple statements, EXPLAIN and direct-record shorthand are rejected by this profiling API. Forward-fetch projections are supported: fetch_batches, fetch_rows_read and fetch_vm_steps separately count successful target SELECT batches and their physical rows/instructions. These counters exclude catalog/schema/savepoint helpers and are zero without target reads. Deduplicated references share target reads. Fetch profiling encloses lowering, outer execution and target reads in one atomic snapshot scope; ordinary fetch limits apply. Counters saturate at u64::MAX. An error returns the usual Error without partial counters. Collection CTEs and supported derived sources run within the primary statement and contribute to its counters. Ordinary execute retains its result shape.

The CLI accepts `.profile SELECT ...` as a standalone command in line/interactive input, or as the entire script input. Its JSON report adds a `profile` object on success and retains rows/columns/affected and transaction state. It is not a batch of commands, so multiple SQL statements are rejected before execution. Node profileSelect bindings expose the same result and counter scope; aggregate profiling of frontend helper work remains unfinished.

Node Database.profileSelect and AsyncDatabase.profileSelect return `{ result, metrics }`, with camelCase bigint counters transported as decimal strings. The async operation uses the existing ordered/bounded worker queue and interruption handle. Typed parameters/results, observed transaction state, errors and closed-connection handling follow execute. No partial counters are returned on failure.

## Managed schema validation at connection creation

Database::connect now validates the catalog and each metadata-referenced collection/index schema in one read snapshot before returning the connection. Missing objects, wrong object/table ownership, changed generated DDL (including uniqueness, columns and constraints), and unexpected explicit indexes or triggers on managed tables fail with FDB_STORAGE. Implicit primary-key indexes remain allowed. Stored DDL is compared lexically against the pinned engine's generated form, allowing whitespace, keyword case, semicolons and the catalog's creation-time IF NOT EXISTS flag. Identifier quoting follows the engine's stored form, including its quoted key column. Busy/interruption and other operational engine errors continue to propagate.

This validation runs at connection creation, not on every subsequent read or before every write. It does not scan stored documents or index contents, authenticate a file, repair corruption, or prevent out-of-band modifications after a connection has been exposed. Existing per-operation metadata/value validation remains in place. Compatible generated schema changes require an explicit validator update and upgrade evidence.

Connection-time validation also inventories schema names beginning with the reserved __fastdb_c_ and __fastdb_i_ prefixes, case-insensitively. Any such object without a corresponding catalog storage entry fails with FDB_STORAGE. This catches missing collection/index metadata, orphan reserved tables/views, and a deleted catalog followed by reopening. Database::open retains its existing behavior of creating a missing catalog table; connect then rejects surviving orphan storage. It does not reconstruct metadata, delete orphan data, or detect data/index-content corruption or arbitrary renamed objects outside those prefixes.

The same inventory rejects physical index storage referenced by more than one collection metadata entry. This checks ownership in addition to DDL shape; two individually valid metadata entries cannot share one managed index table.

## Explicit collection content audit

`Connection::check_collection_integrity(table, IntegrityLimits)` validates managed schema, then audits one collection's documents and indexes in a single snapshot. It streams physical ID/document pairs, verifies canonical typed ID agreement, applies existing value/field/CHECK validation, requires exactly one matching index key/ID entry per document, and checks total index entry counts to detect extras. Missing/null indexed values use the existing index semantics. No data or index repair is performed.

Defaults are 100,000 documents and 64 MiB of processed encoded ID/document bytes. Callers may override either limit; exceeding it returns FDB_LIMIT with no partial report. Limits do not bound engine allocations, time, schema scans or index-query work; an engine row is materialized before its encoded size is checked. The audit retains one document at a time and performs an index lookup per document/index, followed by index counts. Reports contain documents, indexes, index_entries and encoded_bytes.

Detected logical content mismatches return FDB_STORAGE. Engine errors, including interruption during CHECK evaluation, propagate without being reclassified as corrupt data. Ordinary write CHECK error handling is unchanged. This is not a replacement for native PRAGMA integrity_check, physical B-tree/page verification, metadata recovery or full resource/cancellation qualification. Rust callers can use the explicit audit; Node and CLI bindings are described below.

Node Database.checkCollectionIntegrity and AsyncDatabase.checkCollectionIntegrity expose this audit with optional bigint maxDocuments/maxEncodedBytes limits and bigint report counters. The binding rejects unknown limit fields, non-bigint values, negatives and values exceeding uint64 before native submission. Omitted fields retain Rust defaults. Native failures use the existing error/transaction envelope; the async variant uses the existing worker queue.

The standalone CLI command `fastdb-cli --check-collection COLLECTION [--max-documents N] [--max-encoded-bytes N] DATABASE` requires an existing database file and does not read stdin. Limits are unsigned decimal 64-bit integers, including zero; omitted limits use the defaults above. Audit mode cannot be combined with SQL input modes, history, migrations, transfers or their options. Invalid arguments are rejected before opening the database. A missing file returns FDB_NOT_FOUND without creating it.

Success prints one JSON line with `documents`, `indexes`, `index_entries`, `encoded_bytes` and `transaction.before/after`. Audit errors print an `error` object with `code` and `message`, plus transaction observations when a connection was obtained, and exit nonzero without partial counts. Opening/connection failures have no transaction fields. Argument and output-I/O errors use the ordinary CLI stderr failure path. Counts are JSON integers; consumers requiring exact uint64 values must parse them losslessly. Opening uses the normal database initialization/recovery path, not a read-only file mode; the audit itself performs no repair.

## Collated collection range operands

Range lowering now resolves native-column identity through the source scope, including beneath COLLATE, parentheses and unary plus. A collated collection field is lowered as a document expression instead of being emitted as a nonexistent physical column. Differential tests cover text/NULL values with NOCASE and BINARY, both operand positions, all four range operators, and direct, derived and CTE collection sources. Existing binary/numeric mixed-native range and native-column BETWEEN tests also cover parenthesized/unary-plus document operands. This does not qualify binary/record ordering under explicit collation, arbitrary native expressions, or every mixed BETWEEN operand form.

## Document BETWEEN native column bounds

A preserved logical value may be the left operand of BETWEEN/NOT BETWEEN when both bounds resolve to native SQL columns. The logical value converts to a raw scalar (binary payloads remain raw bytes), and the native BETWEEN node applies each bound's affinity and collation. A generated scalar subquery isolates the conversion from physical document-storage collation and preserves one evaluation of the logical left expression. This internal lowering does not add general user-written scalar-subquery support.

Record/scalar ordering fails when either bound is non-null; two null bounds produce NULL. This path also accepts supported column wrappers and typed derived/CTE left values. Native columns are read again for the null-aware record check, so volatile native views/derived expressions remain unqualified. Mixed typed/native bounds and arbitrary bound expressions remain outside this extension. No data/index encoding changes are made.

## Tokenizer input and retention limits

Every FastQL tokenizer invocation accepts at most 16 MiB of UTF-8 input and 262,144 tokens. The byte check runs before scanning or copying token text; it includes comments and whitespace and reports byte offset zero. The token check runs before copying the first excess token and reports that token's byte offset. Comments and whitespace do not count as tokens; quoted text is one token. Exact boundaries are accepted by the tokenizer, though the resulting statement must still satisfy ordinary syntax and semantics. Both errors are parser errors (FDB_SYNTAX), consistent with the delimiter-depth guard.

These fixed bounds apply to direct SQL calls, the entire script passed to batch splitting/completeness checking, and internal uses of the shared tokenizer. Increasing the CLI input buffer does not raise them. An oversized batch fails lexical preflight before any statement executes. Parameter values and non-SQL document APIs use separate encoding/validation paths; these constants are not direct value-size limits, although generated SQL that embeds values is subject to the tokenizer bounds. Limits bound input length and retained token count, not all transient allocations, recursive AST depth, lowering expansion, query execution time or result memory. Flat operator chains and delimiter-free CASE nesting still require full AST qualification.

## Parser stack availability

The pinned native parser limits expression recursion/tree depth to 100, but local debug-build probes found that unary chains and nested CASE could exhaust the caller stack before reaching that error. FastDB now uses pinned stacker 0.1.22 around SQL execution, profiling and collection-audit entry points, plus direct native AST parsing, engine statement preparation and row execution (which can reprepare). The outer entry points allow internal operations to reuse the same auxiliary stack. If less than 16 MiB of stack is available, the callback runs on a requested 32 MiB auxiliary stack on the same thread. Nested protected calls reuse sufficient available stack. There is no database-worker handoff or transaction change.

Native execution and profiling return parser/validation errors for the tested oversized expressions. Native fallback parse errors for collection references are preserved as described below. CLI, two-MiB Rust caller-thread and synchronous/worker Node regressions verify process survival, retained active work and subsequent queries. A schema-change test verifies actual engine reprepare of accepted deep expressions. This is not a whole-process memory cap, an assurance for arbitrary caller stack sizes or a cross-platform stack qualification; frontend recursive lowering and other execution paths still require broader limits.

## Native fallback parse errors

When SQL reaches the native fallback and guard normalization cannot parse it, the guard first checks the original first statement with the pinned native parser. Its actual error is returned through FDB_ENGINE before unresolved collection names or literal text can replace it with a generic managed-lowering rejection. The parser call uses the existing auxiliary-stack protection. Valid statements retain managed-name checks; valid multiple statements retain the single-statement rejection.

The FastQL INSERT SELECT write guard keeps lexical fallback for original syntax that has not yet been expanded. This change does not make malformed FastQL valid, allow unmanaged access to physical storage, or change profiling's existing validation-error wrapper. Differential tests compare ordinary and collection-referencing malformed SELECT/CTE/INSERT SELECT messages with the pinned engine and verify active work is retained.

## Typed VALUES sources and leading WITH inserts

VALUES sources containing expanded FastQL helpers or referenced boolean/record/composite/vector parameters now lower each cell as a typed value. Output metadata covers every column, preserving heterogeneous rows instead of inferring a type from the first row. Standalone results use column1, column2 and so on; CTE column lists and derived-source metadata retain their existing naming/scope rules. Record values no longer escape a VALUES CTE as raw encoded binary. Pure native VALUES sources without logical inputs retain native delegation.

Regression coverage includes heterogeneous rows containing records, encoded-looking Binary payloads, NULL, integers, text, arrays and booleans; record and Binary equality remain distinct. Positional parameters preserve logical identity. A controlled callback verifies each cell of a MATERIALIZED VALUES CTE executes once when the CTE is referenced twice. Arity, missing-parameter and unused-parameter failures leave existing outer work intact. Both Node clients preserve the mixed values and roll back a failed multirow unique-index insert without orphan index entries.

For example, `WITH input(id,n) AS (VALUES (docs:a,1),(docs:b,2)) INSERT INTO docs(id,n) SELECT id,n FROM input RETURNING id,n` now preserves typed IDs and applies collection validation/index maintenance atomically. Native INSERT SELECT targets receive their existing SQL-scalar conversion. A leading WITH on a collection INSERT VALUES is moved into its VALUES source and processed through the same CTE lowerer; sources materialize before target mutation. Duplicate-index and invalid-field failures roll back the statement while retaining supported outer-transaction work.

The extension does not enable scalar/correlated subqueries in VALUES cells, modified standalone typed VALUES, recursive/forward CTEs, fetched VALUES cells or CTE references in unsupported RETURNING/UPSERT expression forms. Native-only leading-WITH VALUES inserts retain their original engine path. Column-list/arity rules and existing parameter validation still apply.

## Typed UNION ALL sources

UNION ALL lowers each supported SELECT or VALUES arm independently and preserves every row, including duplicates. All output cells share typed metadata, preserving heterogeneous records, Binary, booleans and scalar values rather than inferring types from the first arm. Names come from the first arm; arity must match. A managed source or logical input in any arm activates the path. Ordinary native-only compounds retain native delegation; collection INSERT sources can also use scalar-only UNION ALL.

The compound remains one engine query. Generated arm definitions and the compound definition share the user WITH scope; MATERIALIZED user definitions remain shared across arm references. CTE/derived consumers retain typed output columns. ORDER BY accepts output names from any arm, searched left to right, or positions, retaining explicit collation, direction and NULL placement; LIMIT/OFFSET apply to the combined rows. Profiling and both EXPLAIN forms use the compound plan. Result labels still come from the first arm. Arbitrary ORDER BY expressions remain unsupported on this path, consistent with the pinned compound resolver.

Collection INSERT SELECT/VALUES materializes the compound source before atomic document/index writes. Native INSERT targets use the existing single-statement scalar conversion and conflict behavior. Fetched arm projections and scalar/correlated subqueries and broader compound planner/resource/cancellation qualification remain unfinished. This extension does not define composite ordering or add recursive CTEs.

Compound boundary regressions verify later-arm aliases, leftmost-arm precedence, case-insensitive quoted names, three-arm searches, and CTE consumers against native SQL. Anonymous placeholders retain their whole-statement positions across arms and LIMIT. A shared encoded-looking Binary parameter retains raw payload identity in native predicates and typed identity through a managed collection index, in either arm order.

UNION ALL cancellation regressions use a test-only scalar counter and engine progress callbacks during source evaluation, plus total-change-triggered interruption after collection mutation begins. Covered reads and collection inserts return FDB_CANCELLED without a partial rowset, retain existing outer work, and pass source/target collection-index audits. Retrying the same source statement yields the exact expected values. Plain and MATERIALIZED-CTE compound inserts also pass the existing partial-write rollback matrix in autocommit and explicit transactions. These selected deterministic points do not establish per-operation deadlines, cancellation at every engine/frontend instruction, native-target cancellation behavior or cross-platform qualification.

## Typed UNION, INTERSECT and EXCEPT

Supported SELECT/VALUES arms now also support UNION, INTERSECT and EXCEPT, including mixed chains with UNION ALL. Operators combine results from left to right. Native set operations compare each row's SQL scalar keys: NULLs match NULLs, numerically equivalent integers/floats/booleans share equality, native text collation applies, and binary payloads remain distinct from typed record keys. Record target names compare canonically while integer and string record keys remain distinct. Every projected column participates in row equality.

Arms and intermediate sets materialize inside the engine query. Key sets determine membership; a grouped join recovers typed representatives from the source rows without evaluating volatile source projections again. The representative among equivalent values is unspecified, including numeric representation and case-equivalent text. Pure UNION ALL keeps its existing path. This implementation prioritizes value correctness and still requires broader planner, performance and memory qualification.

Typed CTE/derived consumers, output-name/position ordering, pagination and collection/native insert sources use the existing compound pipeline. Collection unique-index failures roll back the statement and preserve tested outer work. Arrays/objects/vectors do not yet have set equality: scalar-key conversion fails if evaluated. A regression observes that such an engine scalar-function error aborts the outer transaction; inspect transaction reports rather than assuming every failed set insert retains prior work. Fetched arm projections, scalar/correlated subqueries and full resource/cancellation/platform qualification remain open.

Set-collation regressions compare 48 two-arm combinations of default/BINARY/NOCASE/RTRIM collation and UNION/INTERSECT/EXCEPT with native SQL, including NULL, ASCII case variants and trailing spaces. Another 64 three-arm cases combine all four compound operators under a shared collation. Comparisons retain duplicate counts while normalizing equivalent text representatives; they do not require the same spelling when the collation equates multiple spellings. Mixed-collation chains beyond two arms and broader Unicode/custom-collation behavior remain unqualified.

The controlled compound-cancellation matrix covers UNION ALL, UNION, INTERSECT and EXCEPT reads and collection inserts at exactly two and four source evaluations, in autocommit and explicit transactions (32 combinations). Retry checks use operator-specific exact results, including an empty intersection. The after-write matrix also covers distinct UNION/INTERSECT/EXCEPT inserts and a VALUES-first UNION, with document/index audits and prior-work checks. These selected source and mutation points preserve the tested transaction state; they do not establish all cancellation points or native-target cancellation semantics.
