# FastQL 2.2.0 language contracts

Working specifications, 2026-10-01. Only entries with linked passing evidence
are implemented. Release/client qualification is tracked in [the checklist](v2.2-tasks.md).
Preserve the 2.1.0 catalog and protocol unless a feature explicitly versions it.

## Ordinary SELECT reference wildcard

Implemented in source; focused and full scoped checks pass. Release artifact
qualification remains pending. See [nested projections](nested-projections.md) and
[working evidence](v2.2-tasks.md). The single-field aliased wildcard uses the
existing bounded resolver and contributes one positional column.

## S1: OMIT (source qualified; release qualification pending)

The focused record-projection suite passes all 15 tests, including three OMIT
regressions. Combined scoped Rust, Node/TypeScript and C ABI checks pass;
exact release artifacts and all-client qualification remain pending.

Initial form:

```sql
SELECT * OMIT embedding, internal_notes, profile.private FROM articles
WHERE published = true ORDER BY id LIMIT 20;
```

This returns the ordinary collection `document` column with the named object
members removed. The source must be one collection. Explicit projections,
joins, relational sources and source-star aliases are rejected in this initial
form rather than choosing which output object to alter. Identifiers and quoted
keys follow existing SQL rules. Paths address the returned document, not source
aliases. Dot paths traverse embedded objects only; a missing member, null or
scalar intermediate value is a no-op. Arrays and references are not traversed
implicitly. Duplicate/overlapping paths are harmless and order-independent.
`id` can be omitted from the result without changing the stored record identity.

Filtering, ordering and pagination read the original document. Omission does
not write data, change validation/indexes, or provide access control. Preserve
typed values in retained fields and enforce result limits on returned values.
Input query, path and value nesting bounds continue to apply. Bound parameters
remain values, and cannot provide omitted field identifiers.
At most 1,024 omission paths, each with at most 64 steps, are accepted. RETURNING
does not accept this SELECT clause. Result bounds count retained values; decoding
the source document still requires memory for the original contents.

The [SurrealQL SELECT reference](https://surrealdb.com/docs/reference/query-language/statements/select)
documents the same placement of OMIT and nested field examples. FastDB retains
its one-object positional result and object-only paths; destructuring and
array traversal require their own contracts. Comparison checked 2026-10-01;
no claim of complete SurrealQL compatibility.

## S3: CONTENT replacement and recursive MERGE (source qualified)

Forms target one fixed record or the matched documents of a collection:

```sql
UPDATE articles:a CONTENT {title: 'Replacement', author: writers:w1} RETURNING *;
UPDATE articles CONTENT $document WHERE author = writers:w1 RETURNING id;
UPDATE articles:a MERGE {profile: {country: 'FR'}} RETURNING *;
```

CONTENT replaces all user fields, including whole nested objects and arrays.
It preserves the target's immutable typed ID. An explicit payload ID must equal
that target's ID, otherwise the statement fails. A missing target is not
inserted. Required fields, checks, unique constraints and every index kind apply
to the full replacement. All matched documents and indexes share one statement
savepoint; evaluation, validation, output-limit or cancellation failure rolls
back the statement while preserving earlier caller work. Bound object values
retain their logical types. Every candidate is evaluated against its original
document before mutations begin.
Fixed targets do not accept an additional WHERE; use a collection predicate for
conditional updates. The existing affected-count and RETURNING conventions apply.

Existing `UPDATE collection { ... }` and `UPDATE collection:key { ... }` keep
their shallow-patch meaning. MERGE combines nested objects recursively when both
values are objects. Incoming arrays, scalars and null replace that entire value;
unmentioned members remain. Neither form uses null to mean removal.
The [SurrealQL UPDATE reference](https://surrealdb.com/docs/reference/query-language/statements/update)
documents whole-object CONTENT and recursive MERGE. FastDB keeps RETURNING and
typed positional results. Future read-only validation must reject replacement
that changes or removes a read-only field; it must not silently bypass checks.

Focused evidence: 13 parser tests; 79 existing/new write tests, seven metered
write tests and 13 write-buffer tests; three CONTENT/MERGE regressions include
all index kinds, failure after a successful mutation prefix, caller work,
concurrent-reader snapshots and reopen. Combined scoped checks and sync/async
Node regressions pass. Exact release artifact qualification remains pending.

## S4: typed PATCH (source qualified; release qualification pending)

```sql
UPDATE articles:a PATCH [
  {op: 'test', path: '/status', value: 'draft'},
  {op: 'replace', path: '/status', value: 'published'},
  {op: 'add', path: '/tags/-', value: 'release'}
] RETURNING *;
```

PATCH accepts an array of add, remove, replace, copy, move and test operations.
The expression is evaluated against the original document; operations execute
in order on the candidate. The same fixed-record/collection WHERE targeting,
immutable ID, validation, statement savepoint and RETURNING rules as CONTENT
apply. Copy/test preserve exact logical types: integer and floating-point values
are distinct, record table names compare case-insensitively, object member order
is irrelevant, and arrays remain ordered. Null is a value; missing is an error.
Records, binary and vectors are opaque values, not traversable containers.

Member paths use [JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) escaping
(`~0` for tilde and `~1` for slash). Empty member names are supported. Parents
must exist. Object add may insert or replace; replace/remove require the member.
Array indices are canonical nonnegative integers without leading zeroes; add
inserts before that position and accepts `-` to append. Move removes the source
before resolving its destination and rejects a parent-to-descendant move.
Unknown operation members are ignored. Operation names are case-sensitive.

This is a bounded typed member-operation subset of
[JSON Patch](https://www.rfc-editor.org/rfc/rfc6902), not complete RFC or
SurrealQL PATCH compatibility. Empty/root pointers are rejected: use CONTENT
for whole-document replacement and DELETE for removal. ID and its descendants
cannot be destinations or move sources; copying or testing the ID is allowed.
The nonstandard text-diff `change` operation is not supported.

Limits per candidate: 1,024 operations, 64 pointer steps, 16 KiB per pointer,
one million operation/traversal/array-shift steps, and 64 MiB cumulative tagged
value bytes across input, copy sources and intermediate documents. Existing
64-level value nesting and statement candidate/result/work bounds also apply.
These deterministic work bounds are not a process heap guarantee. Failure at
any stage discards all candidate changes and rolls back all affected indexes.

## S5: typed array/object helpers (source qualified; release qualification pending)

The pre-2.2 typed helper catalog provided `array::new`, `array::append`,
`doc::get` and `doc::has`, but no typed distinct/flatten or object
keys/entries/construction helper. Engine JSON helpers cannot replace these where records, binary, vectors
and 64-bit integers must remain typed. Added shared pure-value functions for
SQL expressions and document write expressions, without host I/O or closures:

| Function | Contract |
| --- | --- |
| `array::len(array)` | Number of immediate elements as an int64. |
| `array::distinct(array)` | Retain first occurrences in input order using exact logical type equality. Record targets compare case-insensitively and integer/string keys differ. Integers and floats differ; floating-point signed zeroes compare equal. Objects compare by key/value pairs, arrays by ordered elements. |
| `array::flatten(array)` | Flatten exactly one array level, preserving order and non-array elements. |
| `doc::keys(object)` | String member names in deterministic UTF-8 lexical order. |
| `doc::values(object)` | Typed values in the same key order. |
| `doc::entries(object)` | `[key, value]` pairs in that key order. |
| `doc::from_entries(array)` | Build an object from two-element `[string, value]` pairs. Duplicate keys and malformed pairs are errors. |

Each takes exactly one argument of the declared type. Null and missing input
are type errors, not empty containers. Stored null members remain present;
absent members are not invented. Existing `doc::has` distinguishes their presence
while `doc::get` returns null for either. Empty arrays/objects remain valid.
Use `array::new(...)` or bound values for SQL array construction, preserving
SQLite bracket-quoted identifiers.
FastDB uses the already reserved `doc::` namespace for object helpers. It does
not reserve or override the previously user-defined `object::` namespace when
opening an existing database; this is a deliberate spelling difference from
SurrealQL.

Materializing helpers accept at most 100,000 immediate input and output items;
`array::len` only counts and does not impose that item limit. All helpers bound
combined tagged input/output bytes to 64 MiB and enforce existing value depth.
Distinct uses hashed canonical typed encodings, not pairwise quadratic scans.
Retained values preserve the first occurrence's record spelling and float bits.
These helpers do not create indexes or imply an indexed array search.
Reference: [SurrealQL object functions](https://surrealdb.com/docs/reference/query-language/functions/database-functions/object),
reviewed 2026-10-01.

## S2: whole-document FETCH (source qualified)

The existing deferred projection resolver implements whole-document expansion
without an engine callback or a new storage format. The bounded initial
`SELECT * FROM articles ... FETCH author, metadata.editor` form places FETCH last
after WHERE/ORDER BY/LIMIT. It requires a single collection and a whole-document
result; explicit projections, joins, derived sources and combination with OMIT
are rejected. Ordinary SQL uses of `fetch` remain supported as a
table, field or alias.

Expand only explicitly named finite paths in the returned document. Traverse
embedded objects and arrays, resolve a typed record when that named path reaches
it, and preserve other members. Duplicate/overlapping paths must be independent
of list order. A missing field stays missing, a missing referenced record becomes
null, and ordinary scalar values remain values. Cyclic references terminate at
the supplied path depth; no recursive wildcard or graph semantics. Filtering,
sorting and pagination use stored values before expansion. Target reads and
source reads must share a snapshot and the resolver's batching, deduplication,
reference/work/byte limits. No change to stored references or index contents.

The [FETCH reference](https://surrealdb.com/docs/reference/query-language/clauses/fetch)
was reviewed on 2026-10-01. FastDB's key distinction is returning one positional
document column whose selected members are expanded, rather than adding or
overwriting positional columns. Five focused tests, both Node clients and the
full scoped checks pass. Exact release artifact qualification remains pending. At most 1,024 paths of
64 steps each, 16,384 unique references, one million traversal steps, 64 MiB
cumulative target/output bytes and 64 levels of expanded value depth apply.
EXPLAIN and EXPLAIN QUERY PLAN describe the source query without target reads.


## S6: bounded array predicates and object selection (source qualified)

```sql
SELECT items[WHERE active = true AND n >= $min].{n, label} AS selected,
       profile.{city, country} AS address
FROM articles WHERE published = true ORDER BY id LIMIT 20;
```

These are top-level SELECT projections evaluated after source filtering, ordering
and pagination. They compose with existing finite path/index projections and
collection INSERT SELECT. They do not introduce an indexed array search.
Fetched expressions in WHERE, ORDER BY, DISTINCT, RETURNING, native INSERT
SELECT, CTEs and derived projections retain the existing rejection rules.

Predicates preserve matching elements in array order. Bare fields refer to each
element's object members; `this` refers to the element itself, and `this.this`
addresses an object member named `this`. Missing members yield null. Named `$`
and `@` parameters retain ordinary binding rules, including `$this` and `$parent`;
there is no implicit outer-row capture or reserved parameter. Missing bindings
fail even for an empty input array. Null/missing/non-array input returns null;
an empty array or no matches returns an empty array.

The expression subset is literals, object member paths, named parameters,
comparisons (`=`, `==`, `!=`, `<>`, `<`, `<=`, `>`, `>=`, `IS`, `IS NOT`),
`NOT`, `AND` and `OR`. Calls, arithmetic, subqueries, anonymous parameters and
closures are rejected. Both boolean operands are evaluated. Null comparisons
and boolean operations follow FastDB's three-valued rules; only true selects an
element. Numeric comparisons preserve int64 precision. In particular, `IS TRUE`
uses the same typed comparison as an ordinary FastDB collection predicate.
Record elements remain opaque in predicates: compare their typed IDs explicitly;
no target reads occur while filtering. Binary/object/array truth conversion and
unsupported orderings use the same scalar validation as ordinary expressions.

`profile.{city, country}` returns an object containing those existing members,
retaining their types and stored nulls. Missing keys remain absent. Applied to
an array it selects members from each element; non-object elements produce null.
An explicitly traversed record is fetched through the shared bounded resolver.
Bodies accept 1 to 1,024 unique member names, including quoted names; nested
bodies, aliases, wildcard bodies and computed values are rejected. Subsequent
path steps can access the selected object. Source aliases take precedence:
`profile.{name} FROM articles profile` selects from the source document; use
`profile.profile.{city}` to address its profile field.

The predicate bracket must touch its path (`items[WHERE ...]`). Standalone SQL
bracket names and explicit bracket-quoted aliases keep their meaning. The SQL
bracket lexer cannot represent a closing bracket inside a predicate literal;
bind that value as a parameter. This also avoids treating SQL bracket identifiers
as general array literals.

Each predicate is limited to 16 KiB and 256 expression/path nodes. Projection
execution allows at most 1,024 distinct predicates, one million traversal and
predicate-node steps, and 64 MiB of cumulative evaluated predicate values,
including values for rejected elements. Intermediate/returned values and record
reads also retain the resolver's byte, reference and depth bounds. Cancellation
uses existing cooperative boundaries; frontend evaluation has no hard latency
guarantee.

The [SurrealQL idiom reference](https://surrealdb.com/docs/reference/query-language/language-primitives/idioms)
was compared on 2026-10-01. FastDB deliberately limits these forms to its bounded
projection stage, uses `this` for element scope while keeping `$this` bindable,
and does not adopt nested/renamed/computed destructuring bodies or graph paths.
It returns positional typed columns and uses null for missing projected values.
Six focused regressions and full scoped checks pass, including both Node
clients. Exact artifact qualification remains tracked in the checklist.

## S7: typed unnest (source qualified)

Use a table function in the existing SQL FROM pipeline:

```sql
SELECT d.id, element.key, element.value
FROM docs d CROSS JOIN array::unnest(d.items) element
WHERE element.value > 1 ORDER BY d.id, element.key LIMIT 20;
```

The columns are zero-based integer `key` and typed `value`. Empty and
null arrays contribute zero rows to a CROSS JOIN; LEFT JOIN can preserve the
source with null iterator columns. Non-array, non-null input is an error. Multiple
iterator joins produce SQL Cartesian products, with normal WHERE, grouping,
ordering and pagination over expanded rows. Explicit ORDER BY defines result
order; array positions are retained for that purpose. No implicit record fetch.

The existing JSON table-function route supplies SQL planning, but passing
ordinary JSON would erase record/binary/vector types. A bounded adapter passes
tagged values through that iterator and restores their exact logical types.
The initial bounds are 100,000 items in one input, one million expanded items
across adapter invocations in one engine statement, and 64 MiB of cumulative
adapter input/output encodings. Cached CTE and ordinary relational join work
still need the existing statement VM/read-work limits; this is not a universal
limit on every SQL cross product. Resource failure must preserve atomic writes.

The [SurrealQL SPLIT clause](https://surrealdb.com/docs/reference/query-language/clauses/split)
was compared on 2026-10-01. FastDB uses typed unnest with ordinary SQL clause
ordering instead of introducing an output-field SPLIT clause with different
GROUP BY rules. Five unnest regressions, fourteen existing JSON iterator tests,
and both Node clients pass. Combined scoped and release checks remain pending.
Tests cover typed output and labels, null/empty behavior, Cartesian products,
aggregation, byte/item limits even for COUNT, EXPLAIN, indexed source reduction,
snapshots, cancellation, result limits, atomic inserts and reopen.


## S8: field defaults and read-only values (source qualified)

```sql
DEFINE FIELD stamp ON docs TYPE integer REQUIRED DEFAULT 7 READONLY CHECK(stamp > 0);
DEFINE FIELD payload ON docs TYPE array DEFAULT $typed_value;
```

Modifier order is TYPE, optional REQUIRED, optional NULLABLE, optional DEFAULT,
optional READONLY, optional CHECK. DEFAULT accepts a constant expression or typed
bound value, evaluated once when the field is declared and stored as a typed
constant. Field references and function calls are rejected; it is not an implicit
per-insert timestamp or UUID generator. Root array defaults can be bound typed
values. Explicit values, including null, take precedence over a default and must
still satisfy field validation. The Rust API adds `FieldOptions` and
`define_field_with_options`; existing `Field` struct literals remain valid.

Defaults apply to absent fields on insertion, including new UPSERT targets,
INSERT SELECT, import and replacement insert candidates. Ordinary updates,
CONTENT, MERGE, PATCH and existing UPSERT targets never restore defaults. Parent
object defaults are applied before child defaults, then by lexical path order.
A nested default only applies when its parent object exists; it does not create
an otherwise absent parent. Full candidate CHECKs and every index constraint run
after insertion defaults. Definitions validate default type/nullability and all
existing documents, without silently backfilling them. CHECK expressions still
validate actual write candidates and may reject a default value on insertion.

READONLY preserves logical typed value and presence for the lifetime of an
existing record. No-op assignment is allowed. Removal, changing null to missing,
or populating a previously absent read-only field is rejected. Parent replacement
and PATCH cannot bypass it. INSERT OR REPLACE of the same ID also compares the
old record before deletion. Deleting a record remains supported; read-only is a
schema rule, not authorization. An explicit definition overwrite or removal can
remove the rule. The existing Rust `define_field(..., overwrite=true)` replaces
the whole definition, including these options.

Collections with rules require catalog version 5; old metadata without rules
retains its existing format. Subsequent schema changes never silently downgrade
version 5, even after the last rule is removed. Prior binaries reject that
version; retain a pre-upgrade backup rather than attempting an old-binary rollback.
At most 1,024 rules per collection, 64 path steps and 64 KiB encoded bytes for
one default are accepted. INFO reports `has_default`, typed `default` and
`readonly` separately so a null default differs from no default.

The [SurrealQL field reference](https://surrealdb.com/docs/reference/query-language/statements/define/field)
was compared on 2026-10-02. FastDB deliberately uses constant defaults, existing
REQUIRED/NULLABLE and CHECK spelling, and rejection of incompatible existing
data. Computed values are a separate candidate. Focused and release qualification
are tracked in the checklist; implementation alone is not release evidence.


## S9: strict schemas and typed array elements (source qualified)

Keep bare CREATE TABLE collection behavior. Add an explicit
`DEFINE SCHEMA ON docs STRICT` / `DEFINE SCHEMA ON docs FLEXIBLE` operation that
validates existing documents atomically. Strict mode rejects undeclared members,
including nested object members; it never drops user data. Field paths also
permit their object parents. `id` retains its fixed typed identity.

Add `TYPE array<integer>`, the existing primitive field kinds as element types,
`array<record<writers>>`, `array<vector<3>>`, and a nullable element suffix such as
`array<integer?>`. NULLABLE after the type still controls the whole field.
Initial element validation is one level; `array<array>` accepts inner arrays
without defining their contents. Empty arrays are valid. Arrays preserve order
and logical values without coercion. At most 1,000,000 typed array elements are checked per candidate. Native relational tables retain their existing route.

An object or array field can opt into FLEXIBLE to allow undeclared object keys
below it; declared child fields retain validation. This is needed for arbitrary
objects inside arrays because existing field paths cannot declare array-element
members. Strict object arrays without FLEXIBLE reject undeclared object keys.
Avoid silently advertising wildcard field definitions or nested generic type
expressions that have not been implemented.

Use catalog version 5 with strict collection metadata and field options for
array element type/nullability and flexibility. Validate definitions, existing
data, defaults and every new write. Removing or replacing definitions under
strict mode must not leave incompatible stored data. Expose the rules through
INFO FOR TABLE includes `strict`; each field includes `flexible`, `element_type`
and `element_nullable`. `Connection::define_schema` and `FieldOptions` expose
these rules to Rust without changing existing `Field` literals. Non-strict
collections remain the default; `array<any>` is equivalent to untyped `array`.

Strict definitions allow at most 1024 fields and 64 path steps. Strict object
validation charges at most 1,000,000 member/element visits per document. Existing
value depth/encoding, schema read-work and cancellation limits still apply.
Enabling strict mode validates all existing records without rewriting them;
turning it off retains field type/default/read-only rules. Removing a field in
strict mode validates retained documents and rolls back if they would become
invalid. Removing a field in flexible mode retains its existing metadata-only
behavior. A FLEXIBLE subtree allows unknown keys, not invalid declared values.

SurrealDB supports richer nested generic types and wildcard array field
policies. FastDB's object-only declared paths do not address array positions.
This implementation validates immediate elements, including typed records and
vectors, while `array<array>` leaves inner contents untyped. This is an explicit
bounded contract, not a claim of general SurrealQL schema compatibility.
Focused and full source checks are tracked in the release checklist; exact
release artifacts and client qualification remain pending.

## S10: stored computed fields (design; implementation pending)

Select stored calculation on write, separately from insertion-only defaults.
Proposed syntax: `DEFINE FIELD total ON orders TYPE number VALUE (subtotal + tax)`.
The expression reads the candidate document after defaults and before CHECKs,
read-only checks and index updates. It runs on every supported insertion and
replacement path. Supplied values for the computed field are replaced by the
calculation. Ordinary reads return the stored value and do not run calculations.
This makes scalar, full-text, vector and spatial index eligibility follow the
existing declared output type and index contracts.

Use a bounded deterministic expression subset with explicit field dependencies.
Reject parameters, database reads, reference fetches, user JavaScript, clocks,
randomness and unreviewed functions. Reject cycles, including dependencies on
an object containing the computed output; evaluate dependent fields in a stable
topological order. Do not permit overlapping computed output paths. Nested
outputs apply only to existing object parents, matching nested defaults and
required-field behavior. DEFAULT, READONLY and VALUE on the same field are
mutually exclusive; the computed result still obeys type, array and CHECK rules.

A new or overwritten definition must validate both the type and computed value
of every existing record. It does not silently backfill data: callers can fill
existing values through an ordinary atomic update before defining the rule.
Removing the computation retains stored values. Catalog version 5 will carry
this rule before the 2.2.0 format is frozen. INFO must expose its expression.
Bound expression size/nodes, computed field count and cumulative evaluated bytes;
retain statement cancellation, write-buffer and returned-result limits.

Comparison source: SurrealDB [DEFINE FIELD](https://surrealdb.com/docs/reference/query-language/statements/define/field),
read 2026-10-02 (page includes v3.3.0 behavior). Its VALUE clause stores results
on writes; COMPUTED evaluates on reads. FastDB selects the former execution
model and preserves `$value`, `$before` and `$after` as ordinary parameter names,
so none are available implicitly inside persisted expressions. FastDB also
checks existing data when defining the rule; SurrealDB's VALUE/type rules may
instead first apply on each existing record's next write. These are deliberate
compatibility differences, not SurrealQL aliases.

## S11: analyzer configuration (design; implementation pending)

The pinned engine already accepts FTS `tokenizer`, `min_gram` and `max_gram`
options. Expose its default, raw, simple, whitespace and ngram configurations on
managed `CREATE SEARCH INDEX ... USING FULLTEXT WITH (...)`. Persist the selected
configuration, validate catalog and owned DDL consistency, retain the current
default for old definitions, and include the settings in INFO. Query tokenization
must use the same registered analyzer as indexing. Ngrams are substrings, not
prefix-only matching; mixed case, Unicode, punctuation and long tokens require
explicit regression coverage. Native raw/simple/whitespace tokenizers do not
implicitly inherit the default lowercase filter.

Plan `search::analyze('index_name', text)` against the named index's configuration,
with bounded input, emitted tokens and output bytes. Resolve catalog metadata in
the frontend and pass immutable configuration into the scalar callback, without
database reentry. Inspection must share the engine's actual tokenizer construction;
if that requires a public hook, review and isolate the small additive core change
and register its regressions. Do not reconstruct a merely similar analyzer in
JavaScript. Changing settings requires an atomic index replacement/rebuild.

SurrealDB [DEFINE ANALYZER](https://surrealdb.com/docs/reference/query-language/statements/define/analyzer)
(read 2026-10-02, page includes v3.3.0) offers named pipelines and additional
preprocessors/tokenizers/filters. FastDB's planned index-owned configuration is
limited to qualified hooks in the pinned engine; the syntax is not an alias for
those broader pipelines. Source implementation and qualification remain pending.
