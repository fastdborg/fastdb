# FastQL 2.2.0 scope decisions

These decisions resolve evaluated candidates under the user-authorized 2.2.0
scope. They distinguish a product/architecture exclusion from unfinished work.
An implementation being difficult or absent is not a reason to close an item.

## Changefeeds, subscriptions and offline synchronization: won't do

FastDB's embedded API returns finite positional results to its caller. It has no
subscription delivery channel, durable subscriber identity, acknowledgement
protocol, retained event cursor, or retention owner. A database WAL/checkpoint is
an engine recovery mechanism, not a durable client event log: checkpoint and
backup lifecycles cannot provide the promised resumable retention contract.

Adding LIVE SELECT/KILL/SHOW grammar would therefore not implement the requested
behavior. A complete changefeed requires a separately versioned event log and a
consumer lifecycle; offline synchronization additionally needs replica identity,
conflict handling and tombstone retention. Those are a separate delivery/sync
product, not a convenience in the finite embedded document/SQL API. Do not add
that product to 2.2.0 or use the separate private Cloud service to fill the gap.
Applications can run explicit queries and transactions from their host. This
is not a claim that polling is equivalent to a resumable changefeed.

Disposition covers the FastQL.md backlog entry for changefeeds, subscriptions,
resumable retention and offline synchronization. No subscription syntax, client
support, durability guarantee or performance claim is advertised.

## Procedural blocks, stored procedures and events/triggers: won't do

Keep host-language control flow, SQL CASE, explicit transactions and the existing
bounded stored JavaScript scalar functions as the supported application model.
The embedded engine executes SQL statements and FastDB validates complete
candidate documents with atomic index maintenance. Its stored-function sandbox
has no database re-entry or host I/O. LET/FOR/IF/RETURN/THROW blocks, database
procedures and collection events would introduce another execution runtime with
new variable scope, database re-entry, nested failure/cancellation and transaction
ownership rules. Collection triggers would also need to preserve validation and
all managed indexes on their recursive writes; existing raw engine triggers are
not a substitute for that contract.

This additional application runtime duplicates the already available native host
languages and is outside the document/SQL product direction. Do not expose a
partial procedural grammar or turn stored scalar functions into database-writing
procedures for 2.2.0. Existing ordinary SQL behavior is unchanged by this decision.

Disposition covers the matching FastQL.md deferred backlog entry. It does not
remove existing SQL CASE, transaction operations or stored JavaScript functions.
