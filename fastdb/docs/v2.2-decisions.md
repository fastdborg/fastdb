# FastQL 2.2.0 scope decisions

These decisions resolve evaluated candidates under the user-authorized 2.2.0
scope. They distinguish a product/architecture exclusion from unfinished work.
An implementation being difficult or absent is not a reason to close an item.

## Changefeeds, subscriptions and offline synchronization: won't do

FastDB's embedded API returns finite positional results to its caller. It has no
subscription delivery channel, durable subscriber identity, acknowledgement
protocol, retained event cursor, or retention owner. A database WAL/checkpoint is
an engine recovery mechanism, not a durable client event log: checkpoint and
backup lifecycles cannot provide the promised resumable retention contract.

Adding LIVE SELECT/KILL/SHOW grammar would therefore not implement the requested
behavior. A complete changefeed requires a separately versioned event log and a
consumer lifecycle; offline synchronization additionally needs replica identity,
conflict handling and tombstone retention. Those are a separate delivery/sync
product, not a convenience in the finite embedded document/SQL API. Do not add
that product to 2.2.0 or use the separate private Cloud service to fill the gap.
Applications can run explicit queries and transactions from their host. This
is not a claim that polling is equivalent to a resumable changefeed.

Disposition covers the FastQL.md backlog entry for changefeeds, subscriptions,
resumable retention and offline synchronization. No subscription syntax, client
support, durability guarantee or performance claim is advertised.

## Procedural blocks, stored procedures and events/triggers: won't do

Keep host-language control flow, SQL CASE, explicit transactions and the existing
bounded stored JavaScript scalar functions as the supported application model.
The embedded engine executes SQL statements and FastDB validates complete
candidate documents with atomic index maintenance. Its stored-function sandbox
has no database re-entry or host I/O. LET/FOR/IF/RETURN/THROW blocks, database
procedures and collection events would introduce another execution runtime with
new variable scope, database re-entry, nested failure/cancellation and transaction
ownership rules. Collection triggers would also need to preserve validation and
all managed indexes on their recursive writes; existing raw engine triggers are
not a substitute for that contract.

This additional application runtime duplicates the already available native host
languages and is outside the document/SQL product direction. Do not expose a
partial procedural grammar or turn stored scalar functions into database-writing
procedures for 2.2.0. Existing ordinary SQL behavior is unchanged by this decision.

Disposition covers the matching FastQL.md deferred backlog entry. It does not
remove existing SQL CASE, transaction operations or stored JavaScript functions.

## ANN compression and disk-oriented search

Adopt native F16 graph coordinates alongside the existing F32 default. This fits
the current dense-vector index: documents and reranking vectors remain float32,
and the native graph remains a checksummed blob with transactional redo inside
the database. The catalog and graph identity explicitly record its precision.
Measured size, recall, corruption, rollback and recovery evidence belongs in the
release checklist; no research-paper compression factor is claimed for FastDB.

**Won't do: external-file or memory-mapped ANN sidecars.** The pinned native
backend's external-file view does not use the engine's page/VFS/WAL transaction.
A separately mapped graph cannot share the exact reader snapshot, rollback,
checkpoint, backup/restore and crash-commit boundary of the documents and index
redo. Publishing an external filename would introduce another durability owner
and recovery protocol outside FastDB's single-file storage contract. Loading the
existing blob into memory is persistence, not a disk-resident search claim.
A future index integrated with engine pages would be a new storage architecture;
no sidecar or implicit scan is presented as that implementation in 2.2.0.

**Won't do: TurboQuant codecs in the current dense-native index contract.**
The [TurboQuant paper](https://arxiv.org/abs/2504.19874) describes random rotations
and low-bit scalar encodings, with a residual estimator for its inner-product
variant. It is not the backend's F16 conversion. FastDB's native graph contract
uses homogeneous scalar coordinates, backend-owned encoding/serialization and
recoverable graph metadata. TurboQuant needs codec state, codebooks/rotations and
code-dependent distance evaluation; mapping its name to F16 or I8 would be false.
The backend does expose custom metric callbacks, but a callback alone does not
supply a persisted codec, its configuration lifetime or compatible graph
serialization. Replacing the dense representation with an application-owned
research codec would require a separately versioned index family and persistence
contract, outside the adopted native dense-vector implementation. This is not a
claim that TurboQuant is mathematically impossible to implement in a database.

Research checked 2026-10-02 against the paper and pinned USearch 2.26.2 source;
[official Rust documentation](https://unum-cloud.github.io/USearch/rust/index.html)
describes scalar kinds, filtered search and file/buffer views. Native F16 is the
additional compression selected for 2.2.0. Other scalar kinds are not aliases and
are rejected rather than advertised without numeric/recall qualification.
The matching backlog entry is resolved only after the adopted F16 implementation
passes release qualification; these exclusions do not waive its tests.

## Additional array-position write syntax: won't do

Keep typed PATCH as the array-position write interface. It already distinguishes
inserting an element, replacing an existing element, removing it, appending with
`-`, and moving/copying elements. Every operation uses the same evaluated-document
validation, immutable ID, READONLY, computed-field and atomic index maintenance
path. Missing positions fail according to the explicit operation; no sparse array
or implicit padding behavior is introduced.

Do not add a second `SET items[2]=...` or wildcard-position mutation language.
Square brackets already quote identifiers in the inherited SQL grammar, while
FastQL object paths identify keys. Reinterpreting those tokens as mutable array
locations would either change existing SQL meanings or require another special
assignment grammar and separate rules for insertion versus replacement, holes,
negative indexes and multiple selected positions. This duplicates the explicit
PATCH operations without fitting FastQL's preserved SQL assignment contract.
The limitation is on this additional shorthand, not on positional array writes:
PATCH supports them, including parameter-bound typed values and transactional
failure recovery. Read-side array projections remain supported.

Disposition covers the backlog item “Array-position writes beyond the proposed
PATCH work.” The adopted PATCH implementation has source qualification; its exact
2.2.0 artifact gate remains open and is not waived by this syntax decision.

## General brace query language: won't do

Keep fixed-record brace projection as a zero-or-one-row convenience. Do not turn
it into a second SELECT grammar with dynamic/multiple targets, nested selection
bodies and its own WHERE/ORDER BY/LIMIT rules. FastDB's positional SQL result
model already supports these selection operations with collection sources, typed
ID predicates, parameters, joins and explicit bounded projection paths. A nested
brace body would additionally need to choose between positional columns and
object-building output, alias/key collision rules, and predicate timing around
reference expansion. Those are different semantics from the existing fixed-ID
shorthand. Adding another query language alongside SQL does not fit the preserved
SQL/positional-row contract.

Applications use ordinary SELECT with `id=type::record('docs',$key)` or
`id IN($first,$second)`, and standard SQL WHERE/ORDER BY/LIMIT. Explicit wildcard
paths and array/object projections provide the supported finite nested output.
This is a deliberate syntax/product boundary, not a claim that dynamic IDs or
multiple-record reads are unavailable. Existing fixed-record braces stay intact.

## General fetched derived queries and fetched-value SQL expressions: won't do

Reference expansion remains a bounded final-projection stage after SQL has
selected, ordered and paginated source rows. It batches typed IDs by collection
and resolves them inside the same statement snapshot. Stored references may name
different collections; they are not statically bound relational foreign keys.
The native scalar callback interface does not perform database re-entry, and the
finite fetch resolver intentionally runs outside the native statement executor.

Do not move that dynamic database access into arbitrary SQL expressions, recursive
or correlated query scopes, or ordinary derived/CTE sources. Such a change would
make fetch affect query selection and evaluation count, require a database-reading
operator inside the executor, and introduce a new work/materialization boundary.
Silently pre-executing a derived query during preparation would also violate
EXPLAIN behavior, lazy evaluation and optimizer-controlled materialization.
Neither a callback alias nor a hidden eager query supplies that contract.

Use explicit SQL joins when related values affect predicates, grouping or ordering.
Keep record::fetch, relation::fetch, whole-document FETCH and finite nested
projection paths in their supported final-output contexts. This retains the
existing separation between SQL selection and bounded reference presentation;
no general fetched-value expression support is advertised.

## Additional temporal/decimal value domains and general geometry: won't do

FastDB's released numeric domain is signed 64-bit integer and finite binary64.
The pinned SQL engine likewise has integer and floating numeric values. An opaque
Decimal tag stored in a BLOB would not provide exact native arithmetic, aggregates,
affinity, casts, ordering or unique-index comparisons. SQLite-compatible DECIMAL
casts do not establish exact decimal arithmetic. Do not label binary64 values as
Decimal or advertise precision that the executor cannot preserve.

A genuine decimal domain requires coordinated changes to SQL numeric evaluation,
comparison/index keys, overflow/rounding rules, persistent encoding and the seven
native client value protocols. That is a different numeric compatibility contract,
not the bounded document conveniences or additive engine hooks adopted for 2.2.0.
Keep the existing exact integer and finite floating domains. This is an explicit
architecture/compatibility boundary, not a claim that a future engine could never
implement decimals.

Likewise, keep SQL date/time functions over their documented scalar inputs. Do not
introduce new first-class timestamp, duration, calendar interval or time-zone tags
without a matching arithmetic, comparison and serialization contract. An encoded
string can represent application time data but is not a new SQL temporal domain.
This decision does not exclude ordinary date/time helpers and does not classify
all temporal data as a time-series product.

The supported spatial model is a validated two-coordinate Point, spherical
point distance/radius queries, H3 cells and a managed point index. Polygon topology,
line intersection, coordinate-reference-system transforms and general geometry
indexes require different validation, robust topology algorithms and index keys.
A Point index cannot supply these operations, and accepting a geometry-shaped
object is not evidence of GIS support. General GIS is outside this point-location
model. Preserve the existing spatial functions and indexes; do not advertise
advanced geometry through aliases or unindexed approximations.

Disposition covers the remaining richer temporal/decimal and advanced geometry
backlog entry. It introduces no value tags, protocol changes, numerical precision
claims, temporal storage product or general GIS capability.

## Unrestricted recursive and correlated collection queries: won't do

2.2.0 implements typed composite set equality, typed row membership, and a
collection-backed recursive SELECT seed followed by one UNION ALL step. Existing
qualified scalar, EXISTS, IN, correlated derived/CTE and native-affinity forms
remain supported. This closes the useful bounded additions without promising
that every native SQL shape can contain a typed collection value.

The remaining unrestricted promise does not fit the current typed SQL boundary:
FastDB represents document values as tagged blobs and supplies explicit logical
accessors and comparison keys. The engine resolves SQL affinity, collation,
recursive queue identity and correlated execution using its native values and
scopes. A raw blob queue cannot implement logical numeric/record equality for
recursive UNION deduplication. A generated materialization or repeated predicate
can change native lazy evaluation, volatile expression counts, NULL results and
unordered correlated pagination; these are observable compatibility requirements,
not interchangeable execution plans. The regression
`pinned_correlated_unordered_union_pagination_is_not_materialization_equivalent`
in [compounds.rs](../tests/tests/compounds.rs) records such an actual difference.

Do not introduce a second recursive executor, implicit database reads inside scalar
callbacks, or blanket materialization to claim unrestricted support. General
recursive distinct queues and arbitrary mixed native/typed row-affinity scopes
would require a new engine-level typed value/comparison/scope contract, including
how those values participate in queue uniqueness and native affinity. That is a
separate engine architecture rather than an additive document-language feature.

The shipped collection recursion therefore requires one CTE, one collection-backed
SELECT seed and one UNION ALL step, without fetched values, queue ORDER BY/LIMIT,
or nested generated definitions. The native planner also rejects multiple
recursive references and recursive aggregate/window forms. Keep those native
restrictions; they apply even to ordinary relational SQL. Bounded recursion can
use a step WHERE condition, an outer LIMIT and caller work/deadline limits. Typed
row subqueries require matching typed output columns; mixed native affinity is
rejected rather than silently coerced. Ordinary native recursion/row queries,
explicit joins, the qualified correlation matrix and finite document fetching
remain available.

See the [query contract](v2.2-language.md#composite-equality-and-typed-query-boundaries),
[logical lowering](../frontend/src/select.rs), and
[native recursive planner](../../core/translate/planner.rs). Focused tests qualify
supported behavior and explicit failure boundaries; release artifacts remain a
separate gate.
